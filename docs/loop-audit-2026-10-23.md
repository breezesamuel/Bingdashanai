## 0. 一句话结论

| 问题 | 结论 |
|---|---|
| 钱账 / 收费墙 / 额度 / 审计，单点闭环成立吗？ | **成立**，且有回归保护（fail-closed 已修复并复现验证） |
| 端到端（访问→付费→开通→使用→续费→售后）闭环成立吗？ | **此前缺 3 段**：激活/留存无埋点、客户资料无统一视图、售后无协助通道。**今天已补齐** |

## 1. 两条闭环，过去混着说

系统里其实有两条不同的闭环，之前没有区分，导致"看起来闭环了，但收入是 0"。

### 1.1 B2B 线索闭环（旧）

代码：`core/commercial-loop.js` + `core/loop-integration.js`
阶段：获客 → 沟通 → 成交 → 物流 → 履约 → 售后 → 自我进化
统计对象：`leads` / `outbound` / 交付单
问题：这条链**不产生订阅收入**。它的"已触达"曾经把发送失败也算成进展（已修：只认 `ok===true`）。它适合企业定制交付，不是当前主营收。

### 1.2 订阅闭环（真营收，今天才可测）

代码：`core/saas-loop.js`（新增）+ `core/subs.js` + `core/pay.js` + `core/money.js`
阶段：访问 → 参与 → 试用(¥1) → 付费 → 激活 → 留存 → 续费 → 转介绍

**真实数据（2026-10-23 16:26 快照，剔除 108 个本机/探针/回归访客后；匿名访客每 5 分钟清理一次，数字会随时间漂移）：**

| 阶段 | 人数 | 转化率 | 说明 |
|---|---:|---:|---|
| 访问（访客记录） | 145 | — | 未登录按 IP·小时桶，实际人数更少 |
| 参与（用过一次） | 124 | 85.5% | 免费额度足够让人"试一下" |
| 试用 ¥1 | 2 | 1.6% | 两个人走到付钱 |
| 付费（非体验） | **0** | 0% | **没有一个真实付费客户** |
| 激活 | — | null | 分母为 0，拒绝写 0% 假装精确 |
| 留存 / 续费 / 转介绍 | — | null | 同上 |

**结论：漏斗断在"试用 → 付费"，不是断在"系统不好用"。** 124 人愿意用，2 人愿意试，0 人愿意按月付。下一步要研究的是"为什么不付"，不是继续加功能。

## 2. 端到端：每个环节谁写、谁读、断在哪

单一事实源（Single Source of Truth）原则：

| 环节 | 唯一事实源 | 写入方 | 读取方 | 状态 | 断点 |
|---|---|---|---|---|---|
| 身份 | `visitors`（签名 bd_vid） | `visitorOf` | 全部 | ✅ | 未登录按 IP·小时桶，人数会高估 |
| 免费额度 / 收费墙 | `visitors.pools/freeLeft` + `paywall.SECTIONS` | `subs.gatePool` | 前端额度表 | ✅ fail-closed | 无 |
| 下单 | `orders` | `subs.order` | 支付页 / 运营台 | ✅ | 17 笔 pending 超 24h |
| 支付 | 网关回调 / 到账邮件 / 人工核账 | `pay.js` | `money` | ⚠️ | **支付宝/微信网关未开通**，现在只有人工 + 邮件 |
| 开通权益 | `sublist` + `provisional` | `subs.activate` | `gatePool` | ✅ | 无 |
| 使用 / 激活 | `visitors.usageDays/firstUseAt/lastUseAt` | `gatePool`（今天新增） | `saas-loop` | ✅ 今天起可测 | 历史使用轨迹不可回溯 |
| 续费 | `sublist.expireAt` + `renewalState` | 人工/邮件 | 运营台 | ⚠️ | 到期提醒未自动化 |
| 售后 | `tickets` + `assists`（今天新增） | 客户/运营 | 运营台 | ✅ 新通道 | 无屏幕控制（刻意） |
| 退款 | `refundRequests` → 出款确认 | `refund.js` | 运营台 | ✅ | 需人工确认到账 |
| 转介绍 | `visitors.invite` | 下单时绑定 | `subs` | ⚠️ | 有奖励规则，无成功案例 |
| 审计 | `audit` | `store.push/update` 自动写 | 运营台/审计报告 | ✅ | 少数只读接口不写 |

**一条完整的资金链路（正常路径）：**

```
访客签收 bd_vid
  → gatePool 扣免费额度
  → 额度用尽 → 收费墙（fail-closed）
  → /v1/subs/order 建单（pending）
  → 支付（网关回调 / 邮件 / 人工）
  → pay 确认 → money 记账（settled，非自测）
  → subs.activate 开 sublist（或 provisional 24h）
  → gatePool 放行 + 扣档位额度 + 写 usageDays
  → /v1/loop/saas 汇总为漏斗与断裂检查
  → 到期提醒 → 续费 / 退款 → audit 全程留痕
```

## 3. 系统之间如何"协调"和"互动"

不是靠消息总线，而是靠**四个读模型 + 三条铁律**。

### 三条铁律

1. **金额只认 `money`**：`kpi().revenue` 只统计已结算、非自测、CNY 收入；测试单必须打 `selfTest`，虚拟单打 `void_test`。
2. **权益只认 `sublist` + `provisional`**：任何端不得本地判断"已付费"；`gatePool` 是唯一放行口。
3. **身份只认服务端签名**：未签名的 `visitor` 参数一律回落 cookie/anon，防止换 key 刷免费额度。

### 四个读模型

| 端点 | 回答什么问题 | 权限 |
|---|---|---|
| `GET /v1/loop/saas` | 漏斗断在哪？哪些客户付钱没权益/开通不使用？ | 管理令牌 |
| `GET /v1/customer/file` | 这个客户的全部事实：订单、凭证、权益、退款、工单、协助、资产、待办 | 本人 |
| `GET /v1/usage/margin` | 收入、LLM 成本、毛利、覆盖率（成本未知时不报假毛利） | 管理令牌 |
| `GET /v1/audit/summary` | 钱账是否一致、收费墙有没有漏网、队列健康 | 管理令牌 |

这四个模型都读同一份 `db.json` 台账，**没有第二套账**。端上（Web/PWA/EXE）只是显示层。

## 4. 端与端：Web / PWA / EXE / APK 怎么共用一套闭环

| 端 | 定位 | 与主闭环的关系 | 风险控制 |
|---|---|---|---|
| Web | 主入口 | 直连 `/v1/*`，cookie 身份 | 无 |
| PWA | 辅助（安装到桌面/手机） | 同一域名同一 cookie | 缓存只能是只读缓存；离线**不能**开通权益 |
| Windows EXE | 主交付形态（已决策） | 内嵌 WebView 打开同一站点，或本地壳 + 远程 API | 不允许本地记账；token 不落盘明文；升级走签名 |
| APK | **暂缓**（有 10 个付费客户后再做只读伴侣） | 只读查询 + 协助入口 | 不做本地支付/本地权益 |

**跨端一致性的硬约束：**

- 一个访客在 Web 付费，EXE 打开必须立刻是已开通状态——靠服务端 `gatePool`，不靠端上缓存。
- 任何端都不得缓存"已付费"超过一次请求；`/v1/customer/file` 的 `loopState` 是唯一展示依据。
- 远程协助是**同一张 `assists` 表**，Web / EXE 都能发起，运营台统一处理。

## 6. 远程协助：做了什么，为什么**不**做屏幕控制

### 6.1 已实现（今天上线）

```
客户：/assist.html（中/英/阿三语）
  填问题 + 范围 + 联系方式
  勾选同意书（不可默认勾选）
        ↓
运营：/ops.html 新增「协助队列」
  30 分钟未接单 → 超时预警
  接单 → 处理 → 填写结论 → 归档
        ↓
全程：audit 记录 请求/接单/完成/撤回/过期
```

- 24 小时无人接单自动过期，客户可重新发起
- 客户可随时撤回，别人不能替客户撤回
- 速率限制：每 IP 每小时 5 次
- 响应里 `mode` 恒为 `coordination-only`

### 6.2 为什么不做屏幕共享 / 键鼠接管

真正的远程控制需要四样东西，目前**一样都没有**：

1. 单独、可撤回的授权书（不是一句"我同意"）
2. 全程会话录制与留存（出了纠纷能自证）
3. 敏感信息遮蔽（银行、密码、聊天窗口）
4. 一键断开 + 断连即止 + 仅会话期有效

在没有这四样之前做"远程控制"，等于给客户电脑开后门。**本项目明确拒绝**。现在提供的是"有人管你"的确定感，这比一个不安全的远控按钮更有价值。

### 6.3 如果未来要做

需要单独的安全评审：授权书模板、录制存储与保留期、遮蔽规则、断连测试、第三方审计。做完之前，协助入口只做协调。

## 7. 客户是谁：老客户、付费群体、老年用户

> "客户老人"有两种理解，这里都答，避免猜错。

### 7.1 老客户（存量）

- 审计时点 253 条访客记录（匿名记录每 5 分钟清理，现约 221 条）；145 条去重后非内部；5 条订阅记录（1 体验、3 本机、1 探针）
- 行为特征：**免费额度内高频使用，额度用完即走**；没有复购
- 他们不是"客户"，是"试用者"。把他们叫客户，会误导经营判断

### 7.2 付费群体（谁会真的掏钱）

基于产品能力（对话/Agent/知识库/自动化产出）和价格锚（¥99/月），三个候选群体：

| 群体 | 他们要什么 | 付费理由 | 风险 |
|---|---|---|---|
| **A. 小微老板 / 个体户** | 能直接交付的东西：文案、报价单、客服话术、报表 | 省一个兼职的钱 | 需要"成品"，不是"工具" |
| **B. 自媒体 / 电商运营** | 高频产出、批量改写、选题、脚本 | 直接换流量/GMV | 对"每次重新解释"极敏感 |
| **C. 求职 / 副业人群** | 简历、面试、副业方案 | 一次性收益 | 价格敏感，复购最低 |

**建议首发 ICP：B（自媒体/电商运营）**。原因：使用频率高（天然粘性）、产出可量化（容易做案例）、¥99 决策链短。A 用 ¥699 团队席位承接，C 只做 ¥1 体验漏斗，不投入销售。

### 7.3 老年用户（如果字面理解）

- 特征：大字号、语音输入、怕点错、需要"有人接电话"
- 付费意愿：低；但转介绍意愿高（熟人社会）
- **不建议作为首发 ICP**：获客成本高、支持成本高、ARPU 低
- 可以做：无障碍模式（大字号 + 语音 + 一键协助），作为品牌好感，不作为营收主力

## 8. 粘性、频率、复购：定义 + 当前基线 + 30 天目标

| 指标 | 定义 | 当前 | 30 天目标 | 主要动作 |
|---|---|---|---|---|
| 激活率（7 日） | 付费后 7 天内用过 ≥1 次 | null（今天才埋点） | ≥60% | 首次 10 分钟模板 + 一键跑通 + 结果可下载 |
| WAU / MAU | 7 日 / 30 日活跃 ÷ 月活 | 0（今天起） | ≥25% | 每周固定产出（周报/复盘自动生成） |
| 付费活跃率 | 有效订阅中 7 日活跃占比 | 0% | ≥70% | 到期前用量报告 + 使用提醒 |
| 日均使用次数 | 总使用次数 ÷ 活跃日 | null | ≥3 | 把"每次都要配置"改成"一键复用上次" |
| 7 日留存 | 付费后第 7 天仍使用 | null | ≥40% | 第 3 天回访 + 场景模板 |
| 复购率 | 同一客户 ≥2 笔非体验付费 | 0 | ≥15% | 到期前 7/3/1 天提醒 + 升级路径 |
| 转介绍率 | 付费客户带邀请关系 | 0 | ≥5% | 双方各得 7 天（成本可控） |

**粘性的本质不是"功能多"，是"每周有东西产出"。** 所以优先级：模板化产出 > 新功能。

### 沉默客户处理（已进断裂检查）

- 有效订阅 + 14 天未使用 → `dormantPaid`
- 开通 24h 未使用 → `sub_no_activation`
- 处理动作：先问"是不是不会用"，再谈"要不要退款"；不要先推销升级

## 9. 利润最大化（不含涨价，涨价需拍板）

### 9.1 单位经济现状

- 真实到账：**¥1**（体验单），订单 148 笔（其中大量测试单已作废/标记）
- LLM 成本台账：**0 次真实调用** → 毛利无法计算（`costKnown=false`，不报假毛利）
- 结论：**现在算不出 LTV/CAC**。在拿到 LLM 账单和网关流水之前，任何"利润最大化"都是猜

### 9.2 可控的杠杆（按确定性排序）

1. **清悬挂队列**：17 笔待付 + 1 笔凭证 → 每清一笔都可能是一次真实转化或一次差评
2. **支付网关**：人工核账的每单人力成本 ≈ 10 分钟；网关开通后趋近 0
3. **免费额度成本上限**：只给"能展示价值的最小量"，按 section 单独定价（已有 `settings.costPrices`）
4. **模板化交付**：把"每次都解释"变成"选模板 → 出结果"，降低支持成本
5. **三档收敛（待确认）**：体验 ¥1 / 标准 ¥99 / 团队 ¥699（5 席位）——档位越少，选择成本越低
6. **转介绍**：奖励用"天数"而不是现金，边际成本低

### 9.3 定价纪律

- 改价格必须改 `core/subs.js` + 回归 + 备份，且**需用户确认**（本次未改价）
- 任何"限时折扣"必须写进审计，避免价格体系失控
- 企业采购页（¥2,999 / 5 席位 / 年付）可作为高价锚，但不建议现在主推
