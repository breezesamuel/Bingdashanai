# 定价对标与阶梯设计（2026-09）

> 目的：用全网同类竞品的**实测价格**重新校准订阅价，并修掉原阶梯的结构缺陷。
> 落地位置：`core/subs.js` 的 `PLANS_CN` / `PLANS_EN`。

---

## 一、竞品实测价格（2026-09）

| 档位 | 价格 | 代表产品 |
|---|---|---|
| 免费 / 开源 | $0 | Gemini CLI、Cline（BYOK）、Aider、Zed |
| 入门付费 | **$10/月** | GitHub Copilot Pro（最便宜的主流付费档） |
| **中档锚点** | **$20/月** | Cursor Pro、Claude Pro（Claude Code）、Windsurf/Devin Pro、Codex Plus、Manus Pro |
| 重度 | $60–100/月 | Cursor Pro+ $60、Claude Max 5x $100 |
| 顶级 | $200/月 | Cursor Ultra、Claude Max 20x、Devin Max、Manus Pro 40K |
| 团队 | $19–40/席/月 | Copilot Business $19、Claude Team $25、Cursor Teams $40 |
| 年付折扣 | **15–17%** | Claude 年付 $17/月、Manus 官网标省 17% |

**可提炼的三条结构规律**：

1. **$20/月 是 AI Agent 工具的集体锚点**——2026 年主流产品几乎全部收敛到这一档。
2. **年付折扣落在 15–17%**，不是 30%。折扣给得少，反而说明厂商靠月付现金流而非年付锁定。
3. **阶梯是 1x / 5x / 20x 的用量倍数**，不是"月/季/年单纯打折"。

## 二、原定价的两个问题

原阶梯：`¥60/月` · `¥150/季` · `¥500/年`

```
¥60/月
¥150/季 = ¥50/月     ← 比月卡便宜 17%
¥500/年 = ¥41.7/月  ← 比月卡便宜 31%
```

**问题 1：价格信号偏低。** ¥60 ≈ $8.3，**低于主流入门线 $10**。
低于入门线的定价通常无法传达"值这个钱"，也很难靠订阅本身覆盖成本。

**问题 2（更关键）：阶梯方向反了。**
季卡和年卡都大幅便宜于月卡，等于**主动把新客户往年付推**。
但当前是 **0 客户**阶段——最需要的是**低承诺的首单**：

- 月付 = 一个月的服务 + **12 次续费挽回机会**
- 年付 = **一次定生死**，客单价高但流失即归零，0 品牌时转化率极低

原来 30%+ 的年付折扣，等于在还没卖出第一单的时候，就把付款意愿最强的人推去做最不可逆的决定。

## 三、新定价

| 计划 | 中文 | 英文 | 折合月价 | 定位 |
|---|---|---|---|---|
| `t` 首月体验 | ¥1 | $1 | ¥1 | 破冰，每人限一次 |
| `m` 月度 | ¥99 | $12 | ¥99 | 默认锚点 |
| `q` 季度 | ¥269 | $29 | ¥89.7（省 9.4%） | 犹豫时提 |
| `y` 年度 | ¥899 | $119 | ¥74.9（省 24.3%） | 成交后锁客 |

**取舍说明：**

- **¥60 → ¥99（约 $13.7）**：贴着国内 SaaS 心理价位，**仍低于 $20 锚点**，
  刻意留出涨价空间，而不是一步顶到市场锚点再失去试错余地。
- **季卡只给 9%**：比原来 17% 保守。季卡的作用是"给犹豫的人一个台阶"，不是抢年付。
- **年卡给 24%**：高于竞品常见的 15–17%，这是**唯一可以给大折扣的档位**，
  因为年付本来就是"已经成交过、认可价值"的客户，锁客成本最低。
- **加 ¥1 首月体验**：0 客户阶段的真瓶颈是**转化率**，不是价格。
  把"免费试用"变成"一次真实付款动作"（真实付款意愿的门槛远低于试用），
  且续订按 ¥99 走正常价。

## 四、连带修复的商业逻辑漏洞

定价一改，暴露出三个此前一直存在、但金额小到没人注意的问题：

### 1. `activate()` 兜底会白送体验档
`plans.find(id) || plans[0]` —— 加入 `t` 档后 `plans[0]` 恰好是体验档，
非法 `planId` 会白送一个月。已改为兜底到正式月卡 `m`。

### 2. ¥1 体验单可以刷邀请返利
原返利逻辑只看 `o.paid`，¥1 也是 paid。
推荐人拉 10 个人各买一次 ¥1，就能白嫖"10 人 → 返 1 年"。
已加 `isRealPaid()`：金额 ≤ ¥1 的单不计入付费好友。

### 3. 返利按**订单数**累加，可无限刷
两个独立的漏洞：

- `count = paidByInvited.length` 数的是**订单数**而非**人数**。
  自己连买 10 次月卡就能拿满"10 人 → 返 1 年"。
- 返利是**每次付款累加增量**：3 个季付好友 = 1 + 1 + 3 = **5 个月**，
  而规则写的是"返 3 个月"。

已改为**幂等的累计目标公式**：

```
target = 1人→1月, 3个季付及以上好友→3月, 10人→12月   （封顶，不叠加）
added  = max(0, target - 已发累计)
```

配套新增 `visitors.inviteGrantedMonths` 记账，`settleInvite` 可重复调用而不重复发放。
接口新增 `grantedMonths`（累计）字段——档位语义以累计为准。

## 六、抽成与分润口径已统一（2026-09）

原先的真相不是"两套费率并存"，而是**一套是死配置**：

| 口径 | 位置 | 实际状态 |
|---|---|---|
| 阶梯抽成 3%/5%/3% + 广告代管 20% | `settings.platformFee` | **全代码库无人读取**，从未参与任何结算 |
| 合伙人分成 60% / 平台留 40% | `partner.js` 硬编码 | **实际生效的唯一口径** |
| 推广预算池 5% | `money.js` PROMO_RATE | 生效，但那是自留获客成本，**不是抽成** |

即：设置页写着"平台抽 3–5%"，账上实际抽 40%，看板与设置互相矛盾。

**统一后的唯一规则**（`core/partner.js` 的 `feePolicy()`）：

```
平台抽成 = settings.platformFee.revenueTiers 中，按【近 12 个月已结算实收】命中的那一档
合伙人分润 = 100% − 平台抽成        （单层封顶，绝不向下穿透）
非合伙人渠道 = 平台全额留存，仅按 5% 计提推广预算池（那是成本，不是抽成）
```

要点：

- **阶梯分母是平台自身年营收**（`money.annualSettled()`，滚动 365 天，已到账口径），
  不是单笔成交额——否则"抽成"会随每笔大小乱跳。
- 抽成**只算已结算实收**，不含挂账与已核销。按收不到的钱计提 = 凭空放大平台收入。
- 硬夹逼：平台抽成 `1% ≤ pct ≤ 90%`；配置损坏兜底取**中档 5%**（不取最优档）。
- 阶梯乱序会按 `maxAnnual` 重新排序，不依赖配置书写顺序。
- `settings.partnerSharePct` 已**废弃并清零**。若仍被设置为非 0，会与阶梯冲突：
  **按阶梯执行**，同时写审计告警，并在 `/v1/partner` 的 `legacyConflict` / `legacyNote` 里说明。

当前生效值（年营收 ¥0，冷启动档）：**平台抽 3% · 合伙人分润 97%**。

**合规红线未松动**（`test/e2e/suites/fee-e2e.js` 21/21 守住）：单层封顶、零入门费、
无层级计提、锚定真实成交（无成交额不产生分润、不预支不估算）、未验收不计入应得、
重复验收幂等不重复发放。

## 七、漏斗「伪造进展」已修复（2026-09）

### 病根：三层叠加

1. **把计划冒充进展（最严重）**
   `promote()` 原来写 `touch: touches + 1`，把**排定**的触达计划记成了**已发生的触达**
   （同一行还标着 `touchPlanned: true`，明说系统不代发）。而 `close()` 的成熟门槛恰恰是
   `touch >= 2`。于是机器只要排两次计划——一次也没真发出去——线索就自动升级为「商机候选」。
   这与该文件"绝不冒充已发送"的承诺直接矛盾。

2. **单轮级联，5 个阶段形同虚设**
   `funnelStep` 在同一轮里依次跑完 5 段，刚探测到的线索一轮之内就被推到「优化」，
   阶段之间没有任何真实动作。漏斗退化成一条传送带。

3. **越接近成交的线索越不会被处理（饿死）**
   `pickLead` 无差别地"优先没被处理过的（无 touch/tries）"，于是只要同段还存在未被真实触达的线索，
   **已被人工触达过的线索就永远排在池外**，`close()` 永远看不到它。

### 修复

- **拆分计数器**：`planned`（机器排了几次计划，可无限排）与 `touch`（**只有人工确认**才 +1）。
  `close()` 的门槛只看 `touch`，因此"商机候选"必然对应真实的人际接触。
- **新增 `markTouched(id, channel, evidence)`** —— 漏斗里唯一能推进 `touch` 的入口，
  且**强制要求渠道**（无渠道的"触达确认"一律拒绝）。已接 `POST /v1/money/leads/touch`。
- **计划渠道写 `plannedChannels`，绝不写 `channels`**。`channels` 是 `roiBoard()` 归因真实触达的
  唯一依据；把"打算发"混进去会让 ROI 看板把没发出去的投放算成已触达（同一类造假）。
- **单轮不级联**：`ctx.advanced` 集合保证一条线索一轮最多推进一段。
  注意不能在"本段全被排除"时回退取被排除的线索——那等于让防级联失效。
- **按阻塞原因分流**，不再一律回炉：
  | 情况 | 处置 |
  |---|---|
  | `touch>=2` 且 `signal>=66` | → 商机候选（`deal=null`，金额只能人工填） |
  | `touch==0` 且 `planned>=2` | → 长期跟进，`blockedOn:'human-touch'` |
  | `touch==0` 且 `planned<2` | 原地留在「促单」等人工（**不再在优化↔促单间振荡**） |
  | `touch>=1` 但未达标且 `tries>=3` | → 长期跟进，`blockedOn:'below-threshold'` |
  | `touch>=1` 但未达标 | → 回炉重谈（**真实触达与计划数都不清零**） |
- **`促单` 段按真实触达降序取**，修掉饿死问题。
- **看板暴露诚实口径**：`realTouches` / `plannedOnly` / `waitingHuman` / `closeGate` / `blocked` 归因。

### 回归护栏

`test/e2e/suites/leadfunnel-e2e.js` 从 **21/22 → 37/37**。
原来那条 `early-funnel backlog shrank` 断言本身编码了 bug（"自动化应当消化早期漏斗"），
已重写为四条诚实不变量：

- 无人工触达 ⇒ **绝不允许**出现商机候选
- 单轮每条线索最多推进一段
- 无人工触达的线索永远不越过「促单」
- 计划渠道绝不污染真实渠道

### 生产库的真实画面（修复前）

```
线索 230 条：探测 89 · 优化 55 · 长期跟进 85 · 待成交 1
真实触达合计 = 1 次
```

85 条躺在「长期跟进」，正是因为它们当年靠**机器伪造的 touch** 走完了关卡。
机器生产了 230 条线索和约 285 次"假触达"，而真人一次都没动过。
